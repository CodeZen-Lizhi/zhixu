# 成熟框架优先与自研例外门禁

## Context

项目同时包含 HTTP、AI 编排、可观测性、协议解析、数据访问和测试基础设施。这些通用能力已有成熟生态；
若在未调研既有依赖和主流方案前直接自研，会扩大维护面，并让安全修复、兼容升级、文档和人才经验无法复用。
另一方面，领域状态机、授权、证据链和安全写回等差异化规则不能为了套用框架而丢失项目不变量。

## Considered Options

- 默认自研：初期可完全控制，但长期承担协议兼容、安全修复、工具链和文档成本。
- 发现可用库即引入：减少部分代码，但容易造成依赖膨胀，也可能让领域模型绑定框架。
- 成熟框架优先并设置自研例外门禁：复用通用能力，通过 Adapter 隔离框架，同时用证据批准必要自研。

## Decision

- 新增通用基础设施、协议处理、框架能力或第三方集成前，按“项目已有实现 → 标准库 → 已批准依赖 →
  主流成熟框架”的顺序调研，禁止先实现后补选型理由。
- 候选方案必须先满足全部强制约束，包括安全、数据一致性、隐私、部署形态、许可证、运行时兼容和
  可测试性；任一强制约束不满足即不能用覆盖率平均值掩盖。
- 在强制约束全部满足后，以实现前声明的需求及权重计算覆盖度。标准库或成熟框架达到至少 80% 加权
  覆盖时默认采用，剩余差异通过官方扩展点、Adapter 或薄封装完成，不复制框架已经提供的通用机制。
- “成熟”至少要求：仍在维护、有稳定发布与升级说明、文档和测试可用、许可证可接受、安全问题有处理
  渠道，并与项目当前 Go、Node、数据库和部署基线兼容。下载量或流行度不能单独证明成熟。
- 用户明确指定或项目 ADR 已批准的技术栈属于硬约束。更换、绕开或并行引入同类替代方案前，必须向
  用户说明影响并取得明确确认；实现者不得以个人偏好静默改变选型。
- 框架只进入 Presentation、Application 边缘或 Adapter/Infrastructure。领域实体、状态机、权限、审计、
  幂等、证据和安全写回不依赖框架类型，避免框架升级变成领域数据迁移。
- 现有自研实现按收益和风险逐项迁移，不做无行为基线、无回滚路径的批量替换。当前技术栈是否已经迁移
  完成，只由 Manifest、Composition 和验证结果判定，不能仅根据本 ADR 宣称完成。

## Self-Development Exception

确需自研或继续保留自研实现时，对应 ADR 或任务设计必须记录：

1. 需求清单、强制项、权重和覆盖率计算。
2. 调研过的标准库、项目已有依赖和至少一个成熟候选框架。
3. 每个候选未采用的可验证原因，而不是“更灵活”“更轻量”等无证据结论。
4. 自研代码的最小边界，以及不重复实现的框架能力。
5. 安全、兼容、测试、文档、升级和长期维护责任。
6. 可替换接口、迁移/退出路径、回滚方式和重新评估触发条件。
7. 用户对偏离既定技术栈或新增自研基础设施的明确确认。

领域差异化本身可以成为自研理由，但必须说明为何 Adapter、插件或组合方式不能满足约束。少量、稳定且
标准库已经清晰覆盖的代码不需要为了形式引入第三方框架；此时标准库就是优先复用的成熟方案。

## Consequences

- 新增依赖会多一道选型门禁，但可减少重复实现和长期维护成本。
- 80% 是可审查的需求覆盖阈值，不是代码行数比例；强制约束始终是一票否决项。
- 项目保留领域自主性，但通用机制默认跟随成熟生态，并通过 Adapter 控制耦合与退出成本。
- Review 必须检查调研证据、用户确认、Manifest/Lockfile、License、回归测试和文档是否同步。
