# 人工内容保留：契约与实施边界

本方案落实 PRD 已批准的人工批注保留与重新合并要求。全文投影、纯合并/裁决与119存储已实现，生产执行与发布仍未接通；现有覆盖拒绝逻辑不能替代完整验收。具体首版边界以 manual-content-review.md 第 101 行之后的入口复核为准：只吸收受授权工作区文件编辑，不新增 USER Article/WorkingDraft 编辑功能。

## 复用边界

沿用 `internal/platform/gitcli/merge.go` 的固定三方合并契约和 Change Control 的冲突审阅能力。输入为原生成正文、最新人工正文、新生成正文；不新增通用合并算法。现有 `synthesis-item` 标记只用于校验机器管理片段的归属，不能把用户提供的标记直接当作已核验的来源证明。

## 需要同时落地的约束

1. 人工正文必须成为不可变的内容事实，绑定 Authoring ArticleRevision 或受授权目录读取的内容 Artifact、完整 hash 和采集基线。不能只记录“有人改过”，也不能在发布时临时拼接未入库的文本。
2. 保留现有 v1 渲染与投影 hash 的历史重放。支持人工内容的新渲染版本必须在 SynthesisRevision 中保存完整正文或可精确重建正文的持久投影；正文 hash、Authoring receipt、阅读页、导出文件必须指向同一字节序列。
3. 来源证明与人工内容的身份分开。未改写的机器片段保持原 item/source/body_reference；人工改写过的片段不能继续展示成原语义已核验的结论，也不能被另一份主笔记当作原 item 的完整复制。原引用可供复核，但不能冒充修改后的内容证明。人工批注与原内容并列时应保留各自边界。
4. 无关人工段落和批注必须逐字保留。对同一片段的人工修改与 AI 更新使用三方合并；出现冲突则保存可审阅的冲突结果，不创建冒充已合并的发布版本。不得静默选择人工或 AI 一方作为“成功”。
5. 合并请求同时冻结机器基线、人工基线、新生成投影与 merge contract。提交候选前重验 Authoring latest、目标当前修订与工作区文件 hash；任一变化时旧结果失效，重新读取最新内容并合并。
6. 已核实 generated document 没有 USER Article 的可达保存入口，首版不新增人工父版本接入功能。普通 AppendGeneratedRevision 的 AGENT parent/receipt 校验保持严格；未知 USER/SYSTEM 或独立 Proposal 改版沿既有 owner drift 拒绝。
7. 干净合并只产生待审候选；用户审核发布后才移动正式版本。发布前再次变化时仍由原基线检查拒绝，不能以曾经合并过为由覆盖新编辑。

## 接线顺序

- 先确定可表达人工内容且保持追溯真值的 v2 投影/正文契约，再同步 SQL 验证、Authoring owner 与读取页面；不能仅在最终写文件处加 merge。
- 随后把已有 generated candidate 与人工基线接入固定三方合并，保存预览与冲突身份，接入现有审阅/发布路径。
- 最后将普通来源融合与主笔记发布刷新都接到同一个候选合并入口，避免两个路径的人工内容保护行为不一致。

## 必须证明的结果

- 更新索引片段后，事务章节及其中人工批注的实际发布文件字节不变，阅读页和重新打开的历史版本与文件一致。
- 人工和 AI 改写同一处时显示实际差异/冲突，已发布正文不变；裁决后的内容与引用状态一致。
- 预览后人工再次保存、候选后文件再次修改均拒绝旧基线发布；重新合并保留最新人工内容。
- 人工文本不能伪造 item 标记或沿用已失效的来源证明进入下一层正文包含；历史 v1 快照仍可读取并验证。

该设计仍需在实施时对具体 Schema 与公共字段进行代码审查；当前 00117/00118 的覆盖拒绝与局部刷新不能替代上述完整验收。

## 已收敛的三种基线

L 是最新机器候选（和其 AGENT Article），P 是有真实发布证明的当前全文，F 是受授权路径当前文件。新机器投影从 L 得到；若 L 已有人工全文，先合并 Machine(L)/Full(L)/NewMachine 形成候选分支 N，再合并 Full(P)/F/N。P 不存在时只能沿原 CREATE_ONLY 缺失证明；P 存在而文件消失不当作空文恢复。全文、文件采集、合并裁决都需入库且重新核验；发布绑定旧正式 P 和捕获的 F 两个基线。

当前 Workflow 已有 HumanWaitResult 和持久 Human Task，但 SubmitHuman 会完成该等待节点，并非再次执行同一节点。接入合并审阅时应显式考虑后继 apply 节点及版本化定义，不能假设提交人工结果自动重进当前最后一个 synthesis.apply。原四阶段协议与已有 run 的重放不能被直接改写。此处为已读代码的实施约束，不表示新增状态或图已落地。

## 纯预览实施进展（2026-09-15）

`application/synthesis_manuscript_merge.go` 已复用既有 ChangeControl `RevisionMergeEngine` 与 Git adapter，按上述 L/P/F 顺序合并。四项真实 Git 回归证明：P=A、L=A+B 的未发布 B 保留；文件人工备注保留；内层/外层同处修改产生对应 Review 而不返回可应用 Manuscript；重复冻结输入得到相同 fingerprint，文件变化改变 fingerprint；目标缺失/碰撞拒绝。

新增纯裁决重放函数 `ResolveSynthesisManuscript`，要求每阶段 fingerprint 及全部 conflict ordinal 匹配；内层裁决后若外层产生新冲突，仍需独立裁决。最终两阶段裁决及历史排除测试通过，独立审查已关闭，证据见 manual-merge-review.md。

历史不可信 ID 被移除后再出现不能复活：已完整继承历史排除并集，不过滤到当前机器稿 Item 集，三代真实 Git 回归和上限128拒绝行为已验证。当前任意人工全文变化均整篇待复核，可信 Items 为空，历史引用不能冒充修改后正文的来源证明。纯函数不授予审批/来源许可。119 的不可变捕获与 clean receipt 已通过正式迁移目录实库及并发回归；生产 Authoring 双基线发布、Baseline/Proof、冲突工作台仍未接通。
