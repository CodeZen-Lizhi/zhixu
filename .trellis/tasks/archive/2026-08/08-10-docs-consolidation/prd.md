# 收敛 docs 文档体系

## Goal

在不丢失有效需求、设计约束、运维步骤和决策理由的前提下，收敛 `docs/` 的长期事实源，降低同一事实跨 PRD、架构、计划、清单和任务记录重复维护造成的漂移。

用户最终应当能够从单一文档入口快速回答：产品能做什么、必须交付什么、系统如何设计、后续如何推进、如何运行恢复、关键技术选择为什么成立。

## Background

- 迁移前 `docs/` 有 66 份 Markdown、约 16,874 行，其中 60 份位于 `docs/architecture/`；当前已收敛为 32 份 Markdown，包括 11 份常规长期文档、20 份 ADR 和 1 份 ADR 索引。
- 迁移前的 `docs/product/PRD.md` 有 5,124 行，同时承载产品需求、交付状态、逻辑数据模型、接口、测试、页面和实施顺序；当前产品需求、用户行为和任务状态已分别迁入新的权威源。
- `docs/architecture/implementation-plan.md`、`implementation-checklist.md`、`requirements-traceability.md` 与 `.trellis/tasks/` 重复维护计划、状态和追踪关系。
- `docs/product/PRD-outline.md` 是正式 PRD 的前身；`docs/product/2026-08-01-requirement-optimization-list.md` 混合产品需求、技术选型、任务描述和进度。
- 精确 API 已由 `api/openapi/openapi.json` 管理，精确数据库结构由迁移管理，文档不应再维护平行的字段级契约。
- 工作区存在用户未提交修改，尤其涉及 `docs/architecture/adr/README.md`、`technology-stack.md` 和需求优化清单；迁移必须在这些修改基础上进行，不得覆盖或回退。

## Requirements

### R1. 六类长期文档

`docs/` 只维护六类长期信息：

1. 面向用户的完整功能与使用指南。
2. 产品需求与验收清单。
3. 当前有效的技术架构与数据设计。
4. 高层开发路线图。
5. 安装、配置、运行、备份、恢复和排障手册。
6. 关键架构决策记录 ADR。

`docs/README.md` 是唯一总入口，只负责导航、事实源边界和维护规则。

### R2. 每个事实只有一个权威归属

- 产品目标、范围、需求编号和验收标准只在需求文档维护。
- 当前交付状态和详细任务进度只在 `.trellis/tasks/` 维护。
- 当前架构只在架构文档维护；历史理由只在 ADR 维护。
- 精确 HTTP 路径、请求响应 Schema 和错误码以 OpenAPI 为准。
- 精确表、列、约束和迁移顺序以迁移 SQL 为准。
- 命令、配置项和默认值以 CLI help、配置 Schema/示例及部署文件为准；运维手册只解释受支持操作。
- 工程规范由 `AGENTS.md`、`.trellis/spec/` 和面向人工贡献者的单一入口承担，不在 `docs/` 平行维护。

### R3. 无损迁移

- 每个现有文档必须在迁移清单中拥有明确去向：保留、合并、迁入 Trellis 任务产物、由代码事实源替代，或确认完全重复后移除。
- 删除前先迁移独有的需求、约束、失败场景、验收条件、命令和决策理由。
- 保留需求编号、AC 编号、领域术语、配置名、错误码、表名和 ADR 编号的可搜索性。
- 对被移除路径更新长期文档、项目规范、README 和活跃任务上下文；不通过长期保留空壳文件掩盖死链接。
- `.trellis/tasks/archive/` 和 `research/` 中带旧路径、旧行号的历史证据保持原样，由迁移映射解释新去向，避免改写历史事实。
- Git 提交历史作为原始文本的最终恢复手段；本任务额外保留迁移映射，说明内容的新位置或删除理由。

### R4. 可读性

- “一种文档”指一个逻辑事实源，不强制把所有内容压进单个巨型 Markdown。
- 架构允许按职责拆成少量章节，ADR 允许一项决策一份短记录。
- 目标结构必须使读者从 `docs/README.md` 两次点击内进入任一长期文档。
- `docs/user-guide.md` 必须覆盖需求文档中全部用户可见功能，说明功能用途、入口、主要操作、结果和关键限制；不要求复制字段级验收与技术实现。
- 产品需求不得继续夹带里程碑交付日志；架构章节不得复制精确 OpenAPI 或完整迁移定义。

### R5. 范围控制

- 本任务只重组和去重文档，不改变产品语义、架构决策、API、数据库 Schema、代码行为或当前任务优先级。
- 对迁移中发现的事实冲突，仅记录冲突并采用明确的当前权威源，不顺带修改产品或技术方案。
- 不提交、push、发布或删除外部数据。

### R6. 代码对照与持续防漂移

- 文档收敛后的当前状态必须重新对照代码、生产 Composition、直接测试和归档证据，不沿用迁移前任务描述或仅按 child 归档数量判断。
- 对产品交付 M7-M11 与架构质量步骤 0-6 分别形成代码审计，区分“实现存在”“生产装配”“直接自动化证据”“最终验收”和“已移出需求”。
- 审计结论只回填活跃父任务、长期路线图和当前规范；归档任务与 research 历史保持原样。
- 所有活跃任务的 context manifest 通过既有 `task.py validate` 持续校验；父任务 child 计数必须明确标注为 `children done`，不得伪装父 AC 完成度。

## Out Of Scope

- 实现需求优化清单中的功能或技术迁移。
- 修改 OpenAPI、迁移 SQL、生产代码或运行配置。
- 重写 Trellis 工作流和项目编码规范。
- 为历史文档建设独立文档站、全文搜索服务或新依赖。
