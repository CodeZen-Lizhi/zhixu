# Research: Non-replaceable boundaries for introducing Eino

- Query: Determine which responsibilities must remain project-owned when Eino is introduced, and which responsibilities Eino may wrap, for workflow, River/PostgreSQL persistence, human approval, tool policy, safe writeback, model-run audit, and domain validation.
- Scope: mixed (repository implementation/specs plus official Eino documentation)
- Date: 2026-08-06

> 状态：这是新 ADR 合入前的边界研究。ADR-0019 已正式采用 Chat/Callback 与受项目 Port 约束的 Structured
> Output 短 Graph；本文关于 Workflow、权限、副作用、审计和领域校验不可替换的结论继续有效。

## Findings

### Decision

Eino can be used as an implementation detail inside a bounded AI node or as an adapter around a project interface. It must not become the source of truth for business workflow state, authorization, side effects, audit facts, or domain acceptance. The accepted adoption gate currently says the main module has no formal Eino adoption; a new ADR and a complete gate are required before adding it to the production dependency path (`docs/architecture/adr/0013-eino-adoption-gate.md:20-36`).

The practical rule is: Eino may construct or route an untrusted candidate, but the project decides whether that candidate is executable, durable, authorized, and acceptable.

### Permitted adapter shape

The lowest-risk insertion point is a project adapter that implements an existing seam such as `ChatModel`, `EmbeddingModel`, retriever/reranker, or a stream reader. A bounded Eino graph may sit below the project workflow executor, but its public input/output should be project DTOs and project errors, as demonstrated by the isolated PoC (`poc/eino/chatgraph/runner.go:21-168`; `poc/eino/nodeexec/nodeexec.go:1-66`). Eino types should remain confined to an adapter/composition package; domain, workflow storage, proposal/approval, and tool-policy interfaces must not import them (`docs/architecture/adr/0013-eino-adoption-gate.md:11-15`; `.trellis/spec/backend/quality-guidelines.md:29`).

For model calls, the intended nesting is:

`Workflow executor -> ModelRun/RecordingChatModel -> Eino ChatModel adapter -> provider`

This preserves the existing STARTED/terminal ModelCall contract. A graph that autonomously performs multiple provider calls, tool side effects, or durable waits is not a drop-in `ChatModel`; it would need an explicit project workflow contract and persistence integration first.

For tools, the intended nesting is:

`Eino model-facing ToolCall conversion -> project ToolRequestV1 -> project ExecutionService -> registry/executor/persistence`

The Eino node is a transport shim only. It cannot become a second tool registry or a second filesystem/Git path.

### External references and overlapping Eino capabilities

Current official Eino documentation advertises graph orchestration, stream processing, callbacks, ToolsNode, and ADK interrupt/checkpoint recovery ([Eino overview](https://www.cloudwego.io/docs/eino/overview/); [ToolsNode guide](https://www.cloudwego.io/docs/eino/core_modules/components/tools_node_guide/); [callback manual](https://www.cloudwego.io/docs/eino/core_modules/chain_and_graph_orchestration/callback_manual/); [ADK HITL](https://www.cloudwego.io/docs/eino/core_modules/eino_adk/agent_hitl/); [agent extension](https://www.cloudwego.io/docs/eino/core_modules/eino_adk/agent_extension/)). These features are useful inside a node, but they provide framework execution mechanics, not this project's transaction boundaries, immutable bindings, DB-time lease fences, approval authorization, or domain validators. In particular, an Eino checkpoint can resume an agent computation; it cannot authorize a new project attempt or prove a safe writeback.

The repository PoC is intentionally isolated and pins Eino `v0.9.12` plus `eino-ext` OpenAI `v0.1.13` (`poc/eino/go.mod:6-7`). Its report records incomplete River integration, streaming, structured-output, embedding/retrieval/rerank, and provider gates (`poc/eino/report.md:7-28`). Those results are evidence for adapter boundaries, not production adoption approval.

## Caveats / Not Found

- This research started before the task PRD was populated. The finalized planning scope now lives in `.trellis/tasks/08-06-eino-layered-migration/prd.md`; the boundary evidence above remains grounded in the accepted architecture ADR, executable contracts, and current implementation.
- The accepted ADR explicitly says the main module has not adopted Eino. This report does not authorize changing `go.mod`, migrations, public APIs, or workflow state; a new ADR and all adoption gates are prerequisites.
- Eino's current HITL/checkpoint features were not integrated or tested against this project's River/PostgreSQL lease, approval, and writeback contracts. Treat them as optional subordinate mechanics only.
- The logging spec notes incomplete call-site coverage and no guaranteed external OTel exporter (`.trellis/spec/backend/logging-guidelines.md:144-149`); callback integration must not be presented as complete audit coverage.
- No code or schema was changed and no tests were run; this is a read-only boundary study.
