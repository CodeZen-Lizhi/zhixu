# 知识锚点与增量融合设计

状态：本轮已确认需求已实施并完成定向验收，本地服务与 DeepSeek/BGE 配置已启用。真实个人笔记的完整使用体验尚未专项验收，详见 research/remaining-acceptance.md。

## 目标

让用户能够从多个零散笔记中建立面向明确主题和用途的权威汇总笔记，并在后续新增或修改来源笔记后，识别相关知识、执行增量融合，同时保留可追溯的历史版本。

## 背景与已确认事实

- 同一个知识点可能出现在不同整体目标的笔记中，例如 Redis 同时存在于 Redis 专项笔记、数据库专项笔记和面试复习笔记中；这些来源不能因为主题重叠而互相替代。
- 每份来源笔记需要有标签，以及供后端检索使用的极短内容简介；简介不要求前端展示。
- 用户希望 AI 能把多个来源中的相关模块融合成更完整的主题笔记，并在新增来源后继续扩充。
- 现有后端已经存在知识主题、知识声明、来源溯源、不可变版本、合成运行和摘要等相关概念。

## 需求

- 来源笔记可关联多个主题标签，并保存机器检索用的短简介。
- 笔记需具备文章内部的知识目录：记录包含哪些知识及其对应章节/片段位置。整篇简介和标签不能代替局部知识定位；检索先利用元数据定位候选，再读取相关原文用于融合与证据核验。
- 用户可直接提出“整理数据库知识”等目标，从已有知识库检索相关资料、抽取相关模块并形成初版主笔记，不要求先逐篇选择资料或填写元数据。
- 用户日常可以从集中入口阅读主笔记的当前发布版本，按需展开底层来源，不必在零散文件中反复查找。
- 产品默认以主笔记中心为主要入口：用户首先看到主笔记、当前版本、待处理更新和冲突；原始文件作为来源和证据按需展开。
- 不同主笔记可以共享同一底层资料，也可以存在引用、内容包含等知识关系；例如 Java 主笔记中的数据库访问模块与数据库主笔记相关，不因此把整个 Java 主题判定为数据库的上位主题。
- 上游主笔记发布新版本后，自动检查引用方实际受影响的部分，提供提醒并生成局部更新候选，下游正文经用户审核后才发布。单纯存在关联或共享来源不等于正文依赖，不能因此触发无关改写；未发布草稿不作为传播依据。
- 提供来源图谱，展示主笔记、来源资料及共享来源关系，并支持从汇总内容定位到对应来源版本和原文片段。
- 主笔记正文中的章节、段落或知识片段必须能够追溯到具体知识点、来源文件、来源文件版本和原文片段；追溯关系随主笔记版本保存，不能因来源后续更新而改写历史版本的引用快照。
- 新资料影响已有主笔记时，提供可见的更新提醒和待处理入口；此处不预设站外通知渠道。
- 汇总目标必须表达主题方向和使用目的，能够区分“数据库专项”和“Redis 专项”等范围不同的目标。
- 主题方向和层级由 AI 根据笔记标题、正文及已有知识关系归纳；用户无需为每篇来源笔记手工填写分类字段。
- 用户主要通过设置主锚点表达希望持续维护的汇总目标；系统自动为新笔记生成简介、标签、候选主题和锚点关联。
- 用户可从已有笔记或 AI 汇总结果创建锚点；AI 自动提炼锚点名称、主题层级、用途和初始来源范围。
- 汇总目标的纳入依据由 AI 归纳主题、用途/受众和相关内容形成，不要求用户手工配置。AI 只能提出范围调整建议，用户确认前必须保持锚点原范围；接受普通来源关联不代表批准扩大范围。
- AI 融合必须保留来源溯源，并能识别冲突、重复和新增内容。
- 已引用来源被删除或失效时，保留主笔记正文和已保存的历史来源快照，标记受影响内容并提醒用户复核，不自动删除结论。来源不可用不等于结论被证伪；提示需说明实际原因。后续正文修订仍经用户审核发布。
- 未裁决的冲突允许经用户审核后发布到主笔记。必须并列保留不同观点、各自来源、已知适用条件和明确的“尚未裁决”标记；来源未说明的条件标记为未知，不得编造条件或把冲突自动合成确定结论。发布冲突不代表已经裁决。
- 新来源加入或已有来源更新后，系统能够计算其是否与汇总目标相关，并提供融合候选。
- 增量融合默认仅修改受影响内容，保持无关章节原文不变；涉及用户手工修改过的内容时必须明确展示差异，经用户审核后才应用。不得借增量融合静默执行全文重写。
- 新笔记进入知识库时自动触发异步分析，生成机器检索用的短简介、标签、主题层级和与现有锚点的相关性候选。
- AI 发现新笔记与锚点相关时，先生成锚点关联候选；用户可批量接受或拒绝，接受后才进入该锚点的融合候选。
- 融合带来正文实质变化时产生可追溯的不可变版本；用户可以选择一个版本作为当前发布版本，历史版本可查看或回滚。完全重复且未改变结论、适用条件或冲突状态时，仅追加补充来源记录，不生成正文新版本；已有来源关联确认要求仍适用。
- 系统不能把“同名标签”直接等同于“应纳入同一汇总目标”；纳入必须依据主题范围和用途规则。

## 验收标准

- 给定包含 MySQL、Redis、Oracle 的来源笔记，用户可建立“数据库专项”汇总目标，并将相关内容融合为一个可发布版本。
- 给定同样包含 Redis 的面试笔记，系统可将 Redis 模块作为来源纳入数据库汇总，同时保留其面试语境的来源信息。
- 新增 Redis 来源时，系统能推荐关联数据库汇总目标；新增仅包含 Oracle 的来源时，不会仅因同属数据库而自动纳入 Redis 专项目标。
- 混合主题文章中的数据库模块可以通过知识目录定位并参与融合，其不相关模块不会被整篇带入。
- Java 主笔记与数据库主笔记可以共享来源，并展示二者的知识关联；来源图谱能定位引用的具体原文版本和片段。
- Java 主笔记引用数据库主笔记的事务内容时，数据库发布事务变更后，Java 出现对应更新候选且正式正文保持原样，审核发布后才更新。数据库仅修改 Java 未引用且不影响引用语义的部分时，不生成 Java 正文更新。重复处理同一次发布以及相互引用不得无限生成重复候选。
- 用户能从集中入口打开当前发布的主笔记，并查看新资料带来的待处理提醒，无需逐篇翻找原始资料。
- 用户可查看当前发布版本、历史版本、版本来源和每次融合带来的新增/修改/冲突。
- 主笔记中心默认展示当前发布版本，并提供片段级来源追溯、来源图谱、待处理更新和冲突入口；用户可以从主笔记跳转到原始文件的对应片段。
- 删除已引用原文件后，主笔记正文与当前发布版本保持不变；对应知识显示来源已删除和待复核提示，已保存的历史快照仍可追溯。来源失效时展示实际失效原因，不将来源丢失自动判为知识错误；刷新后提示仍然存在。
- 已发布版本不会被静默覆盖；更新必须形成新的候选或新版本，并可在发布前审阅。
- 接受内容完全重复的新来源后，主笔记正文、正文版本号和当前发布版本保持不变，补充来源可查询；重复处理同一来源版本不重复追加记录。历史版本当时的引用快照保持不变，后补来源与之区分展示。
- 主笔记被人工改写后，新来源必须由 AI 结合当前全文语境重新核验；只有确实支持当前内容才算补充完成。仅支持改写前旧结论的来源不能作为当前正文的补充依据，也不能仅存为历史待复核参考后宣称完成。纯补源仍不修改正文、正文版本号或当前发布版本；全文或来源变化后须重新核验。
- 两份来源给出不同结论时，用户可审核并发布保留双方观点的版本；当前正文及重新打开该版本时均显示未裁决状态、各方来源及已知条件，缺失条件不被 AI 补写成事实。
- 新资料仅补充索引知识时，无关的事务章节及其人工批注在发布后保持原文；索引章节中的人工内容若需修改，审阅时能看到对应差异。草稿生成后用户再次修改主笔记，旧草稿不得直接覆盖新内容，必须基于最新内容重新合并并审阅。
- Redis 锚点遇到 MySQL 新知识时，AI 可建议扩大为数据库锚点；建议待处理或被拒绝时，不改变原范围，也不把范围外的 MySQL 内容纳入该锚点融合。确认范围调整后才按新范围评估来源，当前发布正文仍通过融合审阅流程更新。
